## NOTIFY: the e-mail signup

- 🚧 NOTIFY-1 notify-service: `vhrd_notify` (Rust, axum, `server/`), `POST /api/notify` behind nginx on the web server. The body is a form of at most 1 KB with `email`, `list` (only `donguru`), `consent` (the text version shown), `from` (the page) and a honeypot; the address is checked against a narrow ASCII rule (at most 254 characters, one @, letters, digits and `. _ + -` before it, letters, digits, dots and dashes after it) and anything else is a plain 400. Five signups per client an hour (IPv6 by its /64) and twenty per network (IPv4 /24, IPv6 /48), in memory only, the oldest forgotten when full. Signups are appended to a plain file outside the web root, one line each (UTC time, list, address, consent version), fsynced, mode 0600, duplicates kept out (same answer, same timing), an unfinished last line cut off; `vhrd_notify list`, `count`, `export` and `delete ADDRESS` manage it. No cookies, no user text echoed back. Live since 5 Nov 2026; the Deploy workflow ships it (NOTIFY-3 ci-notify). Later option: double opt-in with a confirmation mail
- ✅ NOTIFY-2 notify-form: `vh.notify`, the Donguru signup form on /donguru (#notify) and the front page (06): the address field, the button, one consent line (one mail when the campaign opens, nothing else, how to be removed) with a link to /privacy, a honeypot off screen and the mailto as a fallback line below. Without JavaScript the form posts and the service sends the visitor back to `#notify-ok`, `-bad`, `-wait` or `-err`, shown by CSS `:target`; with it, `site.js` posts with fetch and shows the same message in place. The consent text's version is `extra.notify_consent`. The front page's hero and spotlight buttons read "Learn more about Donguru" and open /donguru/ at the top; the header's Get notified goes to /donguru/#notify, so no button is more than one jump from a form. `just serve` starts a local service beside the site so the form works on the tailnet; the browser check sends the form with and without JavaScript, in both themes, against a local service and its store
- 🚧 NOTIFY-3 ci-notify: the Deploy workflow ships vhrd_notify with the site, so no PC needs a key on the web server. A secret-free job builds a static musl binary with the pinned toolchain and `--locked`; after approval the deploy job uploads it with `deploy/notify.toml` and a manifest (sha256 of each file, a sequence number) as ci-notify, whose key is forced into `rrsync -wo -no-del -munge` on one upload folder. On the server a user path unit of the service's own user, vhrd-notify, starts `vhrd_notify_activate` (crate `server/vhrd_notify_activate`, a static binary root installs from a checked copy): it takes only regular files of the uploader, checks the manifest, writes the release in tpm ship's layout, switches the symlink, restarts, checks the service on loopback by its `x-vhrd-release` header and rolls back to the previous release when that fails, or when a crash or reboot cut an activation off. The workflow then needs a 400 from the new release at https://vhrd.tech/api/notify before it uploads the site. The service is built and shipped only when something that feeds it changed since the live release (its `x-vhrd-release` an ancestor, no change outside the site-only paths); anything unclear ships it, and the input `notify` forces it. `tpm ship` stays as the fallback. - 🚧 NOTIFY-4 double-opt-in: nothing goes on the list until the address's owner presses the button in our confirmation mail. A signup is one line appended to an intake file, the same work and answer for every well-formed address; the service's worker folds it into the store: a new address becomes a pending record with its confirmation mail queued, a pending one gets the mail again at most once a day and three times in all, a confirmed one gets nothing. Pending records are deleted after 7 days. The store is one line per record (random id and nonce, list, address, status, signup time, consent version, confirmation time, mails sent, the mail in the outbox and its retries), rewritten whole and atomically; the first release's lines are read as pending records with a mail queued. `count` and `export` show confirmed records only, `list` shows both. The confirm link opens /notify/confirm/#TOKEN; only the page's button POSTs to `/api/notify/confirm`, so a mail scanner that opens links confirms nothing. Tokens are an HMAC of the record's random id and nonce with a key the service makes on the server (`token_key`, 0600, never shipped); nothing in the store opens a link. - 🚧 NOTIFY-6 mail-outbox: the worker sends the outbox through mail.vhrd.tech, SMTP on port 465 with TLS from the first byte (lettre, rustls with graviola's crypto: no C), as donguru@vhrd.tech, with a login whose password is in a 0600 file outside the release folder (`mail.password_file`). Confirmation mails at most 60 an hour and 300 a day in all, list mails 20 a minute; past that they wait. MAIL, RCPT and DATA go one by one: only a 550, 551 or 553 to RCPT deletes a pending record, a 4xx retries (1 min to 6 h), another 5xx gives that mail up, and a mail server that can't be reached or refuses the login costs no mail a try (the worker waits, up to 30 min). Plain-text mail in 7bit, links on one line; the log has codes and counts, never an address. Without `[mail]` in the settings nothing is sent.
